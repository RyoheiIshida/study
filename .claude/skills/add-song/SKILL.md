# 音ゲーモードの曲を作る

## 最初に確認すること

**このアプリの曲は音源ファイルではない。** mp3 も wav も一切使わず、`frontend/src/music/songs/*.ts` に書いた
データを `AudioEngine` が Web Audio API でその場で合成している。だから「曲を作る」＝
**TypeScript のデータを書く**ことであって、音楽ファイルを探してくることではない。

時間の単位は最後まで「拍(beat)」で通す。秒に変換するのは `engine.ts` の中だけなので、
曲データも譜面も BPM に依存しない形で書ける。

## 著作権の線引き

**実在の流行曲は使えない。** 音源を使わず耳コピして自分で打ち込んでも、複製権・翻案権・
公衆送信権が働く。JASRAC 管理曲でも Web 配信には別途手続きと費用が要る。
「人気の曲を使う」と「著作権に触れない」は両立しない。

一方で **ジャンル・BPM・コード進行・音色・曲の「型」には著作権がない。** 小室進行も丸サ進行も
自由に使える。やるべきことは、流行っている曲の *型* を分析してオリジナルとして組み直すこと。

ユーザーが「あの曲みたいにして」と言ったときは、曲そのものではなく型（BPM 帯・進行・
リズムの刻み・イントロの有無）に翻訳してから実装する。

## 手順

### 1. 型を決める

作る前に、狙う「型」を言語化する。例（ネオンラッシュの場合）:

| 要素 | 決めたこと |
|---|---|
| BPM | 168（高速ボカロポップ帯） |
| イントロ | 無し。1小節目1拍目からフック |
| 刻み | 16分ハット（`'xoxoxoxoxoxoxoxo'`） |
| 旋律 | 基本8分、サビで16分の駆け上がり |
| 進行 | `Am-F-C-G`（小室進行）→ `Am-F-Dm7-E7` |
| 終わり方 | 末尾に導音 G#(80) を置き、次ループ頭の A(81) へ半音で解決 |

### 2. `frontend/src/music/songs/<name>.ts` を書く

`neonRush.ts` が今のリファレンス実装。`Song` 型（`music/types.ts`）の全フィールドを埋める。

```ts
export const xxx: Song = {
  id: 'kebab-case',          // songById のキー。ユニークに
  title: 'カタカナの曲名',      // スタート画面と曲選択ボタンに出る。短く（6〜8文字）
  mood: '雰囲気を1行で',
  bpm: 168,
  beatsPerQuestionScale: 1.5, // ← 下の「3.」で決める。省略すると 1
  beatsPerBar: 4,
  loopBars: 8,                // 曲はこの長さで延々ループする
  chords: [...],              // 長さは必ず loopBars と一致させる
  lead: [...], bass: [...],
  drums: { kick: [...], snare: [...], hat: [...] },
  comboScale: [...],
};
```

**音色は曲側では選べない。** `engine.ts` がパートごとに固定で割り当てる:

| パート | 波形 | ローパス | バス音量 | 備考 |
|---|---|---|---|---|
| lead | `square` | 2600Hz | 0.22 | MIDI 76〜89 くらいが無難。90 超えは耳に刺さる |
| bass | `triangle` | 無し | 0.3 | MIDI 40〜52 が中心 |
| chord | `sawtooth` | 1200Hz | 0.1 | 小節頭に自動で置かれる。曲側では書かない |
| drum | — | — | 0.5 | |

`playTone` の既定は attack 0.008 秒 / release 0.09 秒。**release は曲データから指定できない**ので、
速い曲で `dur` を 0.25拍（BPM168 なら 0.089秒）にすると release 0.09 秒ぶんが次の音に被る。
16分を連発すると音が濁るので、基本は8分にして16分はバーストだけに使う。

### 3. `beatsPerQuestionScale` を決める（速い曲では必須）

難易度ごとの拍数は `chart.ts` の `BEATS_PER_QUESTION` で easy 8 / normal 6 / hard 4 に
固定されている。これは **BPM 100〜140 帯を前提にした値**で、BPM を上げるとそのぶん
1問あたりの秒数が減り、問題を読み切れなくなる（BPM 168 の hard なら 1.4 秒）。

`beatsPerQuestionScale` を掛けて体感の秒数を戻す。目安:

```
scale = Math.round(bpm / 120 * 2) / 2      // 0.5刻みに丸める
```

**0.5 刻みにすること。** 8/6/4 のどれに掛けても整数拍に収まるのが 0.5 刻みだけで、
整数にならないと判定ノーツが裏拍にずれる（`Math.round` で丸められて音とズレる）。

狙う秒数は **やさしい 4.3秒 / ふつう 3.2秒 / むずかしい 2.1秒** 前後。
検証スクリプトが実際の秒数を出すので、そこで確認する。

### 4. コード進行を書く

`synth.ts` の `chordToMidi` が解釈できるのは以下だけ。それ以外は**黙って C メジャーになる**
（無音になるより鳴らすことを優先している）ので、書き間違えても気づきにくい。必ず検証する。

- ルート: `C D E F G A B` ＋ 任意で `#` `b`
- 種類: 無印（メジャー） / `m` / `7` / `m7` / `maj7` / `sus4`

例: `['Am', 'F', 'C', 'G', 'Am', 'F', 'Dm7', 'E7']`

### 5. ドラムを書く

1小節 = 16文字ちょうど。16分音符16ステップを1文字ずつ表す。

- `'x'` = 強く（vel 0.9） / `'o'` = 弱く（vel 0.5） / `'.'` = 休符

配列が `loopBars` より短いと先頭から繰り返される。**最後の1小節だけフィルを入れたいときは
8要素すべて書く**（`patterns[bar % patterns.length]` なので、要素数が足りないと最後まで届かない）。

```ts
kick: [
  'x...x...x...x...',   // 4つ打ち
  'x...x...x..xx...',   // 前のめりのキックを足す
  // ... 8小節ぶん
  'x...x.x.x.x.x.x.',   // 8小節目はフィル
],
hat: ['xoxoxoxoxoxoxoxo'],  // 全小節同じなら1要素でよい
```

### 6. `comboScale` を書く

コンボが伸びるほど上がる判定音の音階。**曲の調と衝突しない音だけ**を昇順で並べる。
ペンタトニックにしておけば外さない。10個くらい。A マイナーなら
`[72, 74, 76, 79, 81, 84, 86, 88, 91, 93]`。

### 7. `songs/index.ts` に登録する

```ts
import { xxx } from './xxx';
export const songs: Song[] = [neonRush, xxx];
export { neonRush, xxx };
```

`songs` に入れた曲がそのままスタート画面の曲選択ボタンになる。
**入れ忘れると誰も辿り着けない。** 現在は初期の4曲を非表示にして、ネオンラッシュとフルドライブの2曲にしてある
（ファイルは残っているので、戻すなら import して配列に足すだけ）。

## 検証する

```bash
node .claude/skills/add-song/verify-song.mjs frontend/src/music/songs/<name>.ts
```

拍がループ内に収まっているか / ドラムが16文字か / `chords.length === loopBars` か /
コード名が解釈されるか（C メジャーに落ちていないか）/ 難易度ごとの拍数が整数か /
1問あたりの秒数、をまとめて出す。

そのあと必ずビルドを通す:

```bash
npm --prefix frontend run build      # tsc + vite build
```

## 落とし穴

- **`beatsPerQuestionScale` の付け忘れ。** BPM 150 以上でこれを忘れると、遊べない譜面になる。
- **コード名の書き間違い。** `Am7b5` `Gadd9` などは解釈されず、警告も出ずに C メジャーになる。
- **ドラムが16文字でない。** 15文字でも17文字でもエラーにならず、リズムが静かにずれる。
- **`chords.length !== loopBars`。** 足りないぶんは先頭から繰り返されるので、進行が意図とズレる。
- **改行コード。** `core.autocrlf=true` なのでコミット時に LF へ正規化される。新規ファイルを
  heredoc で LF のまま書いても git 上は問題ない。ただし**既存ファイルを node スクリプトで書き換えるときは
  CRLF のまま扱う**こと。改行で split して join し直すと、全行が書き換わった差分になる。
- **音を聴いた確認はエージェント環境ではできない。** 構造チェックとビルドまでしか保証できないので、
  「聴いていない」ことは必ず伝えて、ユーザーに `npm run dev`（フロント 5173 ＋ バック 4000）で
  確認してもらう。テンポ・音域・ハットの細かさは実際に聴くまで分からない。
